# Developing the bridge

How the code works and why, for anyone changing it. Setting it up on a machine is in the README.

## What it is
One Node program on the machine that runs Foundry. It keeps a hidden Chromium page joined to the running world as a dedicated GM user, and offers MCP tools over Streamable HTTP so Claude can act inside the world. It talks to Foundry over localhost, ships nothing to players' browsers, and works when no human GM is online.

## Layout
| File | Role |
|---|---|
| `src/config.mjs` | Reads `config.json` (made by `npm run setup`) over defaults. `allowScripts` defaults to false and setup does not write it: the owner adds it by hand. |
| `src/setup.mjs` | Interactive setup. Hides the passphrase as it is typed; pressing Enter at the Foundry-password prompt clears the password. |
| `src/auth.mjs` | OAuth 2.0 provider for the MCP SDK's `mcpAuthRouter`: dynamic client registration, PKCE S256, 24 h access tokens, rotating refresh tokens. New connections are approved on a consent page with the owner's passphrase (scrypt hash; 8 tries per 15 minutes, lockout kept in memory). Tokens live in `data/tokens.json`. |
| `src/foundry.mjs` | `FoundryClient`: launches Chromium, joins the world, re-joins after restarts (watchdog every 15 s), runs functions inside the page, keeps a job queue in the page for long work, keeps the page's last console messages, and can reload the page. The join flow, the in-page helpers, the console buffer and the reload are exported and shared with the sessions. |
| `src/sessions.mjs` | `SessionManager` (only when `allowUi` is true): a second Chromium process, started when the first session opens and closed when the last one ends, with one browser context (own cookie) per fixed account: `gm` and `player` from `uiAccounts`. A session never rejoins by itself: when its page leaves the game it reports `down` until started again. |
| `src/ui.mjs` | Real input and sight on any client (the bridge's page or a session): `act` (a batch of mouse and keyboard steps through Playwright, so the page sees trusted events), `read` (open windows, dialogs, buttons, fields, notifications, selection, targets, scene, combat as text), `look` (a JPEG through CDP's `Page.captureScreenshot` with a scale in its clip, so it is scaled in the browser), `wait` (polls every 300 ms for a dialog, window, chat message, scene change, selector, text, or a change in a small screenshot). Adds no hooks to the page. |
| `src/tools.mjs` | Every MCP tool. Each call is timed and written to the audit log, success or failure. The `session`, `ui_*` and `client_tools` tools exist only when `allowUi` is true; `run_script` and `job_status` take a `target` (`bridge`, `gm`, `player`, `runner`). `fight_wait` and `fight_plan` call Encounter Builder's brain interface on the bridge's own page (below). |
| `src/worker.mjs` | `ApiWorker` (0.4.0): thinks for Encounter Builder's monsters through the Claude API, on only when `anthropicApiKey` is in `config.json` (below). |
| `src/server.mjs` | Express 5 app: auth routes, `/mcp` behind `requireBearerAuth` (stateless: a fresh MCP server per request), `/health`, logging, audit; starts the API worker. |
| `test/stub-foundry.mjs`, `test/run.mjs` | `npm test`: a fake Foundry plus a full OAuth handshake and a call to every tool. The stub tracks who is logged in, records real input in `window.__stub`, and stands in for Encounter Builder's `runner` setting, `fight.current()` and its brain interface (`window.__stubBrain` records waits and plans; set its `event` to have a wait return it) so the guards and the fight tools can be tested. |

## Rules the code keeps
- **No secrets leave the machine.** The passphrase is stored only as a hash; tokens stay in `data/`. Nothing secret is logged. The API key (`anthropicApiKey`, the owner adds it by hand) is sent only to the Messages API, in its `x-api-key` header: never logged, audited, sent to Foundry or shown by a tool (`foundry_status` and `/health` say only whether there is one).
- **No delete tools, no settings tools, no package installs.** `run_script` is the one open door, and only when `allowScripts` is true in `config.json`.
- **Every tool call is audited** to `data/audit.log`: time, tool, arguments, result, duration. Long string arguments are shortened per value, so each record stays valid JSON (0.1.4 fixed a bug where trimming the whole record broke scripts over 600 characters).
- **Functions that run in the page must be self-contained.** They are serialised into the page, so they can't close over Node variables; pass everything as arguments.
- **The UI tools are off by default** (`allowUi` in `config.json`) and work only while one of `uiWorlds` is running (default `pf2-test`). Every call checks both through the bridge's own page, so they also need the bridge connected.
- **Real input goes to the test sessions, not the runner's page.** The runner is the account Encounter Builder's `runner` setting names (read when the module is active), otherwise the bridge's own account. On the runner's page, `ui_act` and a `client_tools` reload need `force: true`, and are refused while a monster turn is busy: `api.fight.busy()` when the module offers it, otherwise `api.fight.current(combat)` on every started combat with state `running` or `submitted`, or `go` set. `testingTurn: true` lets a forced call through while busy: for tests of exactly that, or to clear a turn that has hung without restarting the bridge. Stopping a session whose account is the runner follows the same rule (force, not while busy) and returns a warning, because it takes the runner offline until started again. Reads (`ui_read`, `ui_look`, console) are always allowed. `run_script` has no busy check on purpose: Encounter Builder's own test driver runs through it.
- **A session never takes a login someone else holds.** `session start` reads `game.users.getName(name).active` on the bridge's page first and refuses if the account is online (Foundry allows one login per user, so joining would log the other client out). The session accounts may not be the bridge's own account.
- **Screenshots are returned, never stored.** The audit log holds the call's arguments and outcome, not the image.
- **No hooks.** The bridge registers no Foundry hooks on any page (a handler that returned a value would cancel other modules' handlers). Waiting is done by polling.

## Monster turns from a chat (0.3.0)
Encounter Builder's brain interface (`api.fight.waitForEvent`, `submitPlan`, `checkPlan`, `reportFailure`; its `docs/DEVELOPING.md` describes them) is how whoever thinks for a monster gets a turn and hands a plan in. Two tools put it on the connector, so a chat can run monsters without `run_script`. Both run on the bridge's own page, need only that the module is active there and the account is a GM, and don't depend on `allowScripts` or `allowUi`: they can do no more than a plan can, and the module checks every plan.
- **`fight_wait({cursor, generation, maxSeconds})`.** No generation: the module's hello at once (the thinker's instructions, the schemas, a new generation that retires any older chat). Otherwise the bridge chains in-page waits of at most `fightWaitChunkS` (60 s) until an event comes or `maxSeconds` (default 180, at most 200) runs out, each one a `waitForEvent` with the same cursor, so each also renews the module's listening light. It stops early at any answer that isn't idle (an event, `superseded`) or, between chunks, when the MCP request's abort signal fires (the caller went away; closing the connection aborts it). The answer adds `waited` (seconds) and `waits` (how many in-page waits). An in-page wait can't be cancelled, so a wait can outlive its caller by up to one chunk, and the module's light stays green for 2 minutes after the last chunk began. A result the caller never received is still audited as ok; nothing is lost, because the caller asks again with its old cursor and gets the same event while the turn still waits. **Every call writes to the world, even `maxSeconds: 0`:** the module saves when the thinker last listened (and the hello saves a new generation), so every GM's Monster Turns window redraws. Not marked idempotent: a call with no generation retires the chat that was thinking.
- **`fight_plan({requestId, combatId?, generation, plan | giveUp, check?, model?})`.** Marked destructive: an accepted plan for a monster on Auto runs at once and can change HP. Finds the fight from the request if `combatId` is left out (the module keeps requests on the Combat flag `turns.requests`). A plan (an object or JSON text) goes to `submitPlan` with `{by: "chat", generation, model}`, which waits up to 10 s for the runner's verdict; `check: true` goes to `checkPlan` instead and writes nothing; `giveUp` goes to `reportFailure`. Exactly one of plan and giveUp, checked before anything reaches the page. The module cleans and checks the plan itself; the bridge passes it on as it came.
- **Timeouts:** each in-page wait gets its chunk plus 30 s. A plan call gets 120 s: with the bridge as the runner, `submitPlan` checks the plan before it answers, which can include opening the fight's map (up to three tries) and gathering what the monster senses, then waits up to 10 s more. On a timeout the error says the plan may have gone in and not to send it again. Other tools default to `evalTimeoutMs` (60 s).
- **Inputs:** ids are letters and digits; optional fields may be null; a plan over 7,500 characters is refused before it reaches the page (the module refuses over 8,000 once quoted).
- **Hooks:** the bridge still adds none. Each wait does make the module add and then remove its own `updateCombat` handler on the bridge's page; it returns nothing.
- **How long one call may hold (live, 2026-11-07):** a 200 s `fight_wait` came back; a 600 s one was cut off by the client at 230 s (Claude Code on the web; a claude.ai chat's limit wasn't measured separately). Hence the 200 s cap. A cut-off call loses nothing: the next call with the same cursor gets the same event.

## The API worker (`src/worker.mjs`, 0.4.0)
Encounter Builder's API route (described in that repo's feature doc for it): the owner chose Sonnet by default and Opus for band leaders and for spellcasters two or more levels above the party; the module decides which a monster gets and says so in each event (`model`: "sonnet" or "opus"), and the worker only maps that to a model id (`apiModels`).
- **When it listens.** Every `apiPollS` seconds (default 5) the worker reads the module's `route.wanted()` on the bridge's page: whether a started fight is on the API route, and Wake Angel's latest press (`{ n, at, launch }`). That read writes nothing. With a fight on the route, or a new press, it says hello with `route: "api"` (the module keeps the API thinker's generation apart from a chat's, so neither retires the other) and waits back to back in chunks of `fightWaitChunkS`, each a `waitForEvent(cursor, s, { generation, route: "api" })` that keeps the module's API light on. When a wait comes back idle and no fight wants the API, it stops listening. The first look only notes where Wake Angel's presses stand, so a press from before the bridge started is not a new one; after the bridge's page joins again (a world relaunch, a module update, another world) the presses are counted afresh, since the setting is per world, and the hello is asked for again, since the prompt may have changed.
- **One event.** A `stall` is left to a chat (it asks the thinker to look into something, which needs tools). For a turn, retry, re-plan or choice it posts to the Messages API: `system` is the hello's prompt as one block with `cache_control: { type: "ephemeral" }` (the prompt starts the same every time, so later turns read it from the cache), the user message is a short line and the event as JSON, and for a packet that asks for a ground or walls judgment, a picture of the module's map element when it is on the bridge's page. `max_tokens` is `apiMaxTokens`. While it waits on the API it renews the module's API light every 30 s (`route.alive`), so a slow answer doesn't look like a thinker gone and the turn isn't given to a chat meanwhile (the module also keeps a turn with the thinker it was given to). Each answer's model and cost go onto the fight (`route.spend`) for the History's total, whether the plan lands or not. The answer's JSON (the whole text, or the first `{...}` in it) goes to `submitPlan` with `{ by: "api", generation, model, usage: { in, out, seconds, cost } }`, the cost from the reported tokens and `apiPrices`. An answer with no JSON goes in as it came: the module refuses it in words and its own count of tries decides what follows. If the hand-in throws, times out, or comes back neither taken, nor refused with a try left, nor ignored on purpose (another thinker has the turn, or the route changed), the turn is handed on, so it never waits with nobody on it. An event number already handled is skipped.
- **When it fails.** A busy (429) or failing (5xx) API, or no answer within `apiTimeoutS` (60 s), is tried three times in all, `apiRetryMs` apart and then twice that (every request sent counts against the hourly cap; redirects are refused, so the key can't follow one elsewhere); after that the turn is handed on (`handOff`: the module gives it to a listening chat, then to the GM) and the worker keeps listening. A refused key (401), a refusal (403), an unknown model (404) or a 400 about the credit balance, billing or a usage or spend limit stops it: it writes the reason to the module's note (`route.note({ state: "stopped", reason })`, which also turns the API light off at once), hands the turn on, and does nothing more until a new Wake Angel press, which starts it with a fresh hello (that also clears the note). Past `apiMaxCallsPerHour` requests in an hour (default 120) it stops the same way with state "capped"; a press starts it again and clears the count. Another API thinker's hello (`superseded`) also stops it until a press, so two never take turns retiring each other. With no key it never listens, and answers a press with the note "no-key".
- **What is kept.** Each call is audited as `api-worker` (request, kind, model, seconds, cost, the module's answer), never with the key or the prompt; the log has a line per call. `foundry_status` has `api` (`key`, `listening`, `stopped`, `callsLastHour`, `spent` since the bridge started) and `/health` has `api` ("off", "ready", "listening" or "stopped").
- **Testing:** `apiUrl` points the worker at the stub's stand-in for the Messages API (`/stub/api/v1/messages`, with `/stub/api/mode` to make it answer 401, 500 or text without JSON, and `/stub/api/calls` to read what it was sent, never the key); the stub's module has `route.wanted`, `route.note`, `route.alive`, `route.spend` and `handOff`, driven through `window.__stubApi` (`window.__stubBrain.submitThrow` makes a hand-in throw). `hardFailure`, `failureWords`, `planOf` and `costOf` are exported for the tests.

## The API usage test (`tools/api-test.mjs`, 2026-11-12)
A one-off script the owner runs herself on the bridge's PC (`node tools/api-test.mjs`), not a tool: she chose that over a tool ("I don't think we need a tool for a test"). It is the first step of Encounter Builder's API route: it reads recorded monster turns from Foundry (`<foundryUrl>/assets/api-test/situations.json`, uploaded there from a test session: `{ system, ask, situations: [{ id, title, event }] }`, the system being the module's own `hello` prompt), first makes one tiny call to prove the PC can reach the API, then sends each situation to Sonnet 5.5 and Opus 5.5 three times (run by run, so an early stop still covers everything), the system prompt cached. It writes `api-test-results/results.json` (git-ignored) after every call: tokens by kind, seconds, dollars at the prices in the file, the answer and the plan parsed from it. It stops before any call whose worst case (every prompt token a fresh cache write, the whole answer allowance used) could take the total past $5. It reads `anthropicApiKey` from `config.json` (hers to add; never printed or written anywhere). Nothing happens in Foundry; the plans are checked afterwards with Encounter Builder's `api.fight.checkPlan` on the same situations rebuilt.

## Things that cost time to learn
- The SDK's bearer middleware answers 500 unless `verifyAccessToken` throws the SDK's `InvalidTokenError`. Bad grants must throw `InvalidGrantError`.
- `app.set("trust proxy", 1)`, not `true`, or express-rate-limit refuses to start behind the tunnel.
- What claude.ai's connector flow needs:
  - a 401 with `WWW-Authenticate: Bearer resource_metadata=…`;
  - `/.well-known/oauth-protected-resource/mcp`, whose `resource` equals the URL exactly as the owner entered it;
  - authorization-server metadata with `registration_endpoint` and S256;
  - redirect `https://claude.ai/api/mcp/auth_callback`;
  - a form-encoded `/token`;
  - every endpoint answering within 10 s.
- Listen on both `127.0.0.1` and `::1`: on Windows the tunnel's "localhost" can be IPv6.
- Foundry 14 draws the join form with JavaScript, so wait for the user select before filling it.
- Use full Chromium in the new headless mode (`browserChannel: "chromium"`). The headless shell draws in software, which made map redraws 10x slower.
- Chat HTML → text: turn `<br>` and block ends into newlines before reading `textContent`.
- After the tool list changes, claude.ai keeps the old list until the connector is disconnected and reconnected.
- The bridge's Foundry user must exist in the world, and only the owner can create it. Two clients can't share one Foundry user: never log a browser in as the bridge user.
- A page reload clears `window.__bridge`: reinstall the helpers after every reload (`reloadPage` does). While the bridge's own page reloads, its state is `joining` so the watchdog stands back.
- Playwright's `Browser` has no `process()`; each `chromium.launch` is its own process, which is why the sessions use a second launch rather than a second context in the bridge's browser.
- Scaling a screenshot: CDP `Page.captureScreenshot` takes a `scale` inside its `clip`, so the browser scales it and no image library is needed. Scene coordinates become page pixels through `canvas.clientCoordinatesFromCanvas`.
- Foundry registers every piece of its UI (sidebar, hotbar, HUD, chat log) as an application, so `ui_read` lists only framed ones (`hasFrame` for v2, `popOut` for v1) unless asked for `all`; unfiltered, one read was 60 KB.
- Take a button's position before clicking it: many buttons vanish when clicked (the card redraws), and asking for the position afterwards waited out the whole timeout (10 s, during which a monster turn finished).
- Close a session cleanly: disconnect `game.socket` and leave the page before closing its context, then pause before closing the browser. That is hygiene, not the fix for a stuck login: on 14.370 the **AI** account stays shown as online after its session closes (the same happened earlier to a closed pane tab), while Test Player drops at once through exactly the same close. The leftover doesn't follow a `pullToScene`, so no live page is behind it; a world relaunch clears it. Until then `session start gm` is refused, which is the right answer for a login the bridge can't see.
- An error thrown inside the page comes back from `page.evaluate` as "page.evaluate: Error: <message>" followed by the browser's stack: keep only the message before it reaches anyone (the API worker's hand-on reasons, found by its tests in 0.4.0).
- Playwright locators auto-wait for visibility, so filter with `{ visible: true }` before `.first()`; otherwise a hidden duplicate of a button makes a click wait until its timeout.

## Testing
1. `npm install`, then `npm test`. Every check must pass (154 at 0.4.0, about 3 minutes). Add a check for every new tool or fix. The run ends by restarting the bridge with `allowUi` off to prove the UI tools are absent then.
2. Then test live through the connector, in the test world: status, every changed tool, a script if scripts are on, a map job if map tools changed, and for the UI tools a comparison with a real browser (a module button, a double-click after a hover, a canvas token drag, a held-key action), since the stub only proves the events arrive trusted. Say which tools were not exercised live.

## Releasing
1. Bring this file up to date with the change: run `python3 tools/doccheck.py` (it lists names this file mentions that are no longer in the code; `WWW-Authenticate` is expected, the SDK sets it) and reread the sections the change touched.
2. Bump `version` in `package.json` and in the `McpServer` constructor in `src/server.mjs`.
3. Commit and push.
4. Build a zip without `node_modules`, `config.json` or `data/`.
5. The owner unzips it over the install folder, keeping `config.json` and `data/`. They run `npm install` if dependencies changed, then restart the bridge window. If tools changed, they reconnect the connector. New config keys (`allowUi`, `uiWorlds`, `uiAccounts`, `anthropicApiKey`) are added to `config.json` by hand; setup does not write them. The API worker's other keys (`apiUrl`, `apiModels`, `apiPrices`, `apiMaxCallsPerHour`, `apiPollS`, `apiMaxTokens`, `apiTimeoutS`, `apiRetryMs`) have defaults in `src/config.mjs` and need no line unless changed.

## Keep out of this repo
`config.json`, `data/`, and any campaign content. The repo is public.
